## 0. Kết luận trước (nói thẳng)

- **`vifast-rt` CÓ THẬT và CHẠY THẬT**: crate `v2/user/rt/` (`lib.rs` + API heap), ELF `u1a.elf`
  **16.736 B**, nạp bằng `run /u1a.elf` trên ảnh sản phẩm riscv64, in đủ evidence `# u1a: …`,
  `Exit(0)` ⇒ `# product halt: shell_exit=0` (log boot thật, §2.2).
- **Nợ KT-346 (a)(b)(c) — ĐÓNG CẢ BA**: (a) runner seed `/hello.elf` + `/u1a.elf` vào đĩa bằng
  `vifast-fsutil` (mkfs + put-file + **đọc lại so byte**); (b) API `proc_fs::read_file` đọc **cả
  tệp** vào buffer (không phải `OP_CAT` 24 B/lần); (c) `proc_exec` dùng
  `vifast_plat_riscv64::exec::exec_bytes` — **không còn** `include_bytes!` cho ELF U-mode.
- **TAP ba arch**: xem §4 (ma trận 27/27 + aarch64 46 + x86_64 47 — kết quả từng lượt ghi ở §4;
  phần chưa chạy lại được vì khoá máy đo ghi rõ là **nợ**, không tô hồng).
- **Nợ còn lại**: allocator vẫn là **arena tĩnh 8 KiB**, **chưa** phải `Untyped` thật (U-mode chưa
  có cap `Frame`/`Untyped`); `Tcb.Exec(path)` vẫn chờ `KT-360`; `.vidl`/kiểm chéo/UEFI mới là
  **đặc tả** trong `v2/docs/u1-uefi-readiness.md`.

`vifast-rt` (API an toàn) là crate riêng. `--cfg rt_alloc` chỉ bật cho `u1a.elf` ⇒ ELF
`shell`/`hello`/`procsrv` **không đổi** đường biên dịch.

### 1.2 exec đọc ELF từ FS (nợ KT-346 (a)(b)(c))

- **Runner** `v2/test/boot/product-riscv64.sh`: `build_fsutil` (build host một lần) + `seed_disk`
  (mkfs + `put-file /hello.elf /u1a.elf` + `get` so byte bằng `cmp`) chạy **trước mỗi boot**; thêm
  phép kiểm **ELF không nhúng** (`RUN OK`/`# hello: run ok`/`# u1a: rt up` phải **0** hit trong
  ảnh) + boot riêng `check_rt` (`run /u1a.elf`).
- **`proc_fs.rs`**: `pub fn read_file(fs, path, buf) -> Result<usize, FsError>` — đọc **cả** tệp
  qua `Fs::lookup`/`info`/`read`; tệp lớn hơn buffer ⇒ `Invalid` (fail-closed, không cắt ngầm).
- **`proc_exec.rs`**: bỏ `static HELLO_ELF = include_bytes!`, thêm buffer scratch
  `Scratch<[u8; 24 KiB]>` (trong `.bss`, **không** trên stack — KT-73/75 tràn guard page 64 KiB),
  `service(…, fs: FsArg)` đọc FS rồi `exec::exec_bytes`; log đổi sang
  `# product exec: path=… src=fs bytes=… …`.
- **`plat-riscv64/exec.rs`**: tách `exec_bytes(m, bytes, …)` (không cần `'static`); `exec()` cũ
  (bảng ảnh) chỉ còn cho ảnh `ktest`.
- **`static_slot.rs`**: `Scratch<T>` (ô `static` **tái dùng** cho buffer tuần tự) — `unsafe` nằm ở
  crate `vifast-plat-riscv64` (D2-17).
- **`build.rs`**: build shim+rt với `--cfg rt_alloc`, build `u1a.elf`, **xuất** `hello.elf`/`u1a.elf`
  ra `target/<triple>/release/user-elfs/` (đường xác định, chỉ trong `target/`).

## 2. Bằng chứng

### 2.1 Build + ngân sách

- `cargo build -p vifast-kbin-riscv64 --features product-all`: **xanh**; `hello.elf` **8.496 B**,
  `u1a.elf` **16.736 B** (arena 8 KiB là `.bss` NOBITS, không vào file).
- `.data+.bss` ảnh sản phẩm riscv64: **249.048 B** < trần **262.144 B** (còn 13.096 B). Baseline
  trước KT-347 cùng cây đo được 224.472 B ⇒ buffer 24 KiB + heap là phần tăng.
- `.corespace`/`size_of::<Machine>()` = 184.792: **không chạm** (không sửa `core_bridge`).

### 2.2 `u1a.elf` chạy thật (log boot, không phải suy diễn)

```
# shell: run path=/u1a.elf
# product exec: path=/u1a.elf src=fs bytes=16736 pid=… check=1
# u1a: rt up heap_bytes=8192
# u1a: vec n=16 sum=376
# u1a: alloc-string:376
# u1a: heap used=…/8192          ← >0: allocator cấp thật (không phải hằng)
# u1a: rt done
# product halt: shell_exit=0
```
(Đây là log của lượt **probe** `check_rt` trên ảnh `product-all`; lỗi `heap used=0` lần đầu đã
được tìm ra và sửa: lưu offset **đầu** thay vì `bump.used()`.)

### 2.3 exec đường `hello.elf` đọc từ FS

```
# product exec: path=/hello.elf src=fs bytes=8496 … check=1
```
(cùng boot: `RUN OK`, `# hello: run ok`, `shell_exit=0`). Trước KT-347 cùng dòng này **không** có
`src=fs bytes=` và ELF nằm trong ảnh.

## 3. Hai đột biến ĐỎ

### 3.1 Bỏ panic handler ⇒ **không link** (đột biến i)

Bỏ khối `#[panic_handler]` khỏi `v2/user/rt/lib.rs` (bản sao `/tmp/rt_nopanic.rs`), build rlib rồi
link `u1a.rs` bằng đúng dòng lệnh của `build.rs`:

```
error: `#[panic_handler]` function required, but not found
error: aborting due to 1 previous error
```

⇒ panic handler của crate là **bắt buộc thật**, không phải trang trí.

### 3.2 Arena quá nhỏ ⇒ fail-closed **có tên** (đột biến ii)

Hạ `HEAP_BYTES` 8192 → **64**, build lại ảnh, boot `run /u1a.elf` (log boot thật):

```
# u1a: rt up heap_bytes=64
# u1a: alloc fail size=64 align=8 used=32/64
# product halt: shell_exit=95 fault_seen=1 events=2 proc_up=1
```

⇒ OOM **không** panic mù, **không** treo, **không** trả null cho `alloc` đoán tiếp: in **tên** +
`used/cap` + thoát mã riêng **95**; `fault_seen=1` là `Exit` của chương trình (không phải panic).
(Lượt thử `HEAP_BYTES=256` **không** chạm OOM — đo được `heap used=250/256`, tức PoC dùng 250 B;
đó là lý do chọn 64. Hoàn nguyên 8192, build lại, `heap used=…/8192` xanh — §2.2.)

## 6. Nợ (nói thẳng)

1. **Allocator chưa trên `Untyped`**: arena tĩnh 8 KiB trong `.bss` của chương trình; U-mode chưa
   có cap `Untyped`/`Frame`. API `vifast-rt` giữ nguyên khi KT-362 thay lõi.
2. **`Tcb.Exec(path)`** vẫn chờ ABI v1.2 (`KT-360`) + `APPROVED`; KT-347 đóng phần *đọc ELF từ FS*
   ở đường kernel-mediated (`EP_EXEC`), không mở `spec/`.
3. **`v2/docs/u1-uefi-readiness.md` là đặc tả**, chưa có `.vidl` mới/stub/`rt::idl`, chưa có script
   kiểm chéo — việc của `KT-362`/`KT-363`/`KT-364` (ghi rõ ở §5 tài liệu).
4. **Buffer exec 24 KiB** chặn trên ELF 24 KiB; ELF lớn hơn ⇒ `err=6` (fail-closed). Khi có
   `Tcb.Exec` nên đọc thẳng vào Frame của ảnh đích thay vì buffer.
5. **Đo bị khoá**: các cổng QEMU (§4) có thể chưa chạy hết trong khung nếu Lead còn giữ khoá —
   ghi nguyên trạng, không tự nhận PASS.
